## 自Linux 6.9起，LUKS挂起不再擦除内存中的磁盘加密密钥

Since Linux 6.9, LUKS suspend stopped wiping disk-encryption keys from memory

**发布时间**: 2026-07-02

**链接**: [https://mathstodon.xyz/@iblech/116769502749142438](https://mathstodon.xyz/@iblech/116769502749142438)

**描述**:

自 Linux 6.9（2024年5月）起，全磁盘加密（LUKS）的密钥在系统挂起时未从内存中清除，导致加密形同虚设长达两年多。作者通过 Git bisect 定位到原因：一次内核重构（commit a28d893e）与加密代码产生了意外的长距离交互。修复仅需一行代码，并已提交补丁。此外，作者还开发了用于 NixOS 的“secure-suspend”项目，通过内核补丁在挂起时擦除 LUKS 密钥，并包含集成测试以避免未来回归。该问题最初是在整理 Debian 的 cryptsetup-suspend 的 NixOS 移植时发现的。

**评论要点**:

当前稳定版为Trixie，Bookworm默认内核6.1，6.12可通过backports安装。帮助台每天处理2-300名用户登录后忘记密码的问题，这种思路在大型终端用户组织中不适用。关于安全：仅在休眠后拥有代码执行能力才有效，且机器需永久对用户不可用。若能读取RAM中的密钥，则已完全控制操作系统，无需伪造或提前执行代码；若能在休眠前执行代码，同样能获取密钥。

## 如何向陌生人求助

How to ask for help from people who don't know you

**描述**:

向陌生人寻求帮助的关键在于“设身处地为对方着想”。首先，展示自己是一个值得帮助的严肃的人，通过提供证明（如作品、博客、项目）或个人推荐来建立可信度，但机构信誉最弱。其次，解释背景时要极其简洁，将你的情况与对方已知的事物关联。然后，让请求易于接受：降低时间与精力成本，具体明确，提供低摩擦选项（如可转发的简介），并限定范围，避免长期义务。最后，让对方容易拒绝，避免施压或情感绑架；真诚接受“不”，维护未来合作可能。寻求帮助是技能，而非天赋。

## 代码审查的主要目的是发现难以维护的代码

The primary purpose of code review is to find code that will be hard to maintain

**发布时间**: 2026-07-02

**链接**: [https://mathstodon.xyz/@mjd/115096720350507897](https://mathstodon.xyz/@mjd/115096720350507897)

**描述**:

Mark Dominus认为许多人误解了代码评审的目的。他指出，代码评审的主要目的并非让评审者查找bug或确保代码无bug，因为通过检查代码来发现bug通常是不可能的，依赖此方法会陷入虚假的安全感。真正的目的是发现难以维护的代码：评审者尝试理解代码的逻辑与实现方式，若无法理解，则表明未来维护将困难，应在原作者仍熟悉代码时修复。Dominus补充说明，将评审目标从“找bug”改为“检查是否理解”更现实可行——前者费力且不确定，后者任务明确，只需记录不理解的代码，成功率高且容易判断完成时刻。部分回复指出这一观点与SML/NJ重写经验相符，并强调评审中的提问有助于知识传递和设计改进。

**评论要点**:

评论核心观点如下：第一，代码的可接受性取决于是否能够理性推理其行为，例如能否判断代码是否会终止，否则不可接受。第二，团队文化起决定作用，如果领导允许且不会因此得到差评，可以尝试某些做法，但现实中很多人无法做到。第三，强烈反对自动压缩提交（auto-squashing），因为它会创建缺乏作者语义意图的大型提交。在大规模代码审查中，应保留清晰、小型的语义提交，以便于审查和理解。

ZeroFS 是一个日志结构文件系统，专为 S3 兼容对象存储设计。它通过 NFS 和 9P 协议提供 POSIX 文件系统访问，通过 NBD 提供原始块设备支持，所有服务运行在单一用户态进程中。写入数据被分割成 32 KiB 的块，打包成最大 256 MiB 的不可变段，上传前经过压缩（zstd/lz4）和加密（XChaCha20-Poly1305），热读使用本地缓存。系统经过严格测试（pjdfstest、xfstests、内核编译等），支持地理分布，可通过 ZFS 跨 S3 区域创建镜像。存储引擎支持 TRIM、检查点、读取副本，并具有内存/磁盘缓存。

**评论要点**:

评论核心观点：用户对ZeroFS能够同时读写数千块硬盘的能力表示好奇，认为可能催生新用例。但指出该项目有广告推广嫌疑（如在Twitter投放广告）。重点质疑其“数据丢失窗口”的位置（节点间还是客户端与基础设施间），认为文档中“Honest fsync”声称失败转移时未刷新的写入会返回错误，但未明确说明写入延迟不可控（节点间延迟不在ZeroFS控制内）。此外，用户认为基准测试中顺序写入和追加写入以`success: true`对应fsync，但怀疑其可靠性，需要更详细的说明。整体认为文档对关键风险（如延迟、一致性）的阐述不足。
