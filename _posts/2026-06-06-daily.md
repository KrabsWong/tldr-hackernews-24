## 改变Ladybird的开发方式

Changing how we develop Ladybird

**发布时间**: 2026-06-05

**链接**: [https://ladybird.org/posts/changing-how-we-develop-ladybird/](https://ladybird.org/posts/changing-how-we-develop-ladybird/)

**描述**:

Ladybird 项目宣布不再接受公开的 Pull Request，代码变更仅由项目维护者引入。此举旨在为即将到来的 alpha 版本建立更紧密的开发流程、更清晰的安全模型，并缩小代码责任范围。主要原因在于 AI 工具大幅降低了贡献门槛，使得提交看似有价值但可能隐藏恶意漏洞的代码变得更快更便宜。对于浏览器这类处理不可信网络输入的项目，这增加了安全风险。项目将关闭所有现有公开 PR，也不接收通过其他渠道提交的补丁。Ladybird 仍保持开源，外部贡献者可通过 bug 报告、网站测试、标准讨论、安全报告和设计反馈等方式支持项目。

**评论要点**:

代码的价值在于实现新功能，而非单纯堆砌代码量；同时，软件绝非“纯粹技术”，其道德与社会责任不可忽视——它关乎文明存亡，开发者应避免冷漠与剥削，始终以改善人类生活为目标。此外，知识不应被封锁，社区参与可设门槛，但信息传播必须自由开放。

## 追踪欧洲上空的强GNSS干扰源

Tracing a powerful GNSS interference source over Europe

**发布时间**: 2026-06-05

**链接**: [https://arxiv.org/abs/2606.03673](https://arxiv.org/abs/2606.03673)

**描述**:

本文分析并识别了一个自2019年起对欧洲大陆、格陵兰及加拿大造成多次强瞬态广域干扰的天基GNSS干扰源。基于2019至2026年地面参考站网络数据，文章（1）开发了基于接收功率的检测框架；（2）详细描述了干扰事件的空间、时间及频谱特征；（3）提出并分析了融合接收功率与到达时间差的识别方法；（4）应用这些技术确认该干扰源为俄罗斯部署在“闪电”（Molniya）轨道上的预警卫星星座。

**评论要点**:

评论核心观点：1）干扰行为看似愚蠢，但若被用作通信渠道，会暴露自身意图，与炫耀式干扰无异；2）导弹依赖GPS制导，只有导弹来袭时实施干扰才能使其脱靶，但干扰信号本身也会成为预警，尽管不提供具体位置；3）欧盟曾天真地认为对俄罗斯友善能换取其转变，但俄罗斯外交本质是“欺凌和说谎”，如今正为此付出代价。

pg_durable: Microsoft open sources in-database durable execution

**描述**:

pg_durable 是微软开源的 PostgreSQL 扩展，旨在将持久执行能力嵌入数据库内部。它允许用户定义由 SQL 步骤组成的函数，在数据库崩溃、重启或步骤失败时自动从最近的检查点恢复执行，无需手动重建状态。该扩展适用于需要容错后台任务的场景，如向量嵌入管道、数据导入、定时维护、扇出聚合和外部 API 调用等。它替代了传统上使用 pg_cron 加状态表、外部编排工具（如 Airflow、Temporal）或复杂应用层代码的方案，解决了长事务重做、部分失败手工清理、工作流分散在多个组件等问题。使用 pg_durable，工作流定义、重试状态、进度跟踪和检查点均集中在 PostgreSQL 中，简化架构并提升可观测性。

## 约定式提交鼓励关注错误的事情

Conventional Commits encourages focus on the wrong things

**发布时间**: 2026-06-05

**链接**: [https://sumnerevans.com/posts/software-engineering/stop-using-conventional-commits/](https://sumnerevans.com/posts/software-engineering/stop-using-conventional-commits/)

**描述**:

文章批评了《Conventional Commits》规范，认为它存在两大问题：一是导致关注点错位（Focus Failure），二是未能兑现承诺（Broken Promises）。该规范将提交类型（如fix、feat）置于首位，而把范围（scope）设为可选项。作者指出，对于贡献者、调试者、事件响应者等角色，范围（即影响的具体代码区域）才是最关键的，因为他们需要根据范围来理解变更、定位问题。而类型信息反而无关紧要，因为任何类型的提交都可能引入缺陷。因此，将范围降为可选项的做法是错误的。文章认为，该规范虽然被广泛使用，但实际效果适得其反，未能真正帮助开发者和用户理解变更。

**评论要点**:

评论核心观点包含三点：第一，希望代码格式化工具更强大，能根据设置规则自动修正缩进（类似`gofmt`覆盖操作而非直接修改文件），并借此使“goto fail”类错误更明显；第二，强调Git本身已有机器可读数据结构，结构化数据应存入该处，而非占用人类可读文本字段；第三，个人经历指出：当工具由不同团队维护、组织从Jira迁移至GitHub Issues时，旧系统中的信息未能迁移，最终随Jira关闭而丢失，揭示了跨系统数据迁移失败的普遍问题。

Gemma 4 QAT models: Optimizing compression for mobile and laptop efficiency

**描述**:

谷歌发布Gemma 4 QAT模型，通过量化感知训练（QAT）优化压缩，大幅降低内存占用（如E2B文本模型降至1GB），同时保持模型质量。相比传统后训练量化，QAT在训练中模拟量化过程，减少质量损失。针对移动设备，团队设计了定制量化方案：静态激活减少实时计算、通道量化适配移动加速器、对生成层采用2位压缩、优化嵌入与KV缓存，提升效率并支持长对话。内存需求方面，E2B（文本）Q4_0约1.4GB，移动格式约0.8GB；E4B及26B模型亦有显著降低。新权重已在Hugging Face提供Q4_0和移动格式，支持llama.cpp、vLLM等工具，便于开发者部署至边缘设备与消费GPU。

**评论要点**:

1. 质疑方法有效性：询问是否有证据表明该量化方法能保持准确性，并指出其听起来类似mxfp4 with gpt-oss（发布时令人困惑的模型），暗示可能需要更多验证。
2. 对E2B模型的负面评价：用户反馈即使未量化的E2B模型在最简单的现实世界分类任务中也完全无用，进一步质疑该路线的实际可用性。
