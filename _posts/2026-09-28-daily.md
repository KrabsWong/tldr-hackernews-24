## 编码问题尚未解决

Coding is not solved

**发布时间**: 2026-09-28

**链接**: [https://blog.alexewerlof.com/p/coding-is-not-solved](https://blog.alexewerlof.com/p/coding-is-not-solved)

**描述**:

作者基于自身构建AI系统的经验，反驳“编码已被解决”的说法。他指出LLM生成代码虽降低了创建成本，但维护、可靠性、安全等非功能性需求才是软件成本主体，且AI无法被问责，因此医疗、金融、航空等低容错领域仍需人类理解与负责。文章还批评了“规格即代码”“英语是新编程语言”“品味即价值”等观点，认为AI是能力放大器而非替代品，过度依赖AI会损害工程质量与开发者自身价值。

**评论要点**:

自己动手解决问题能真正理解问题，后续修改代码时也更得心应手；依赖他人写代码，出问题时不仅要额外理解对方的思路，还得做同样的修复工作。除非永远不遇到需要自己介入的难题，但现实中几乎每个项目都会碰到。另一方面，有人认为在适当监督下，AI可以辅助“聪明但懒”的人达到“聪明又勤奋”的效果；也有人指出，一个改动若波及范围过大、破坏了无关测试，即便初衷是好的，也很难被合并。

**描述**:

作者认为，AI 生成代码本身并非核心问题，更大的隐患是个人或团队不再了解系统架构以及某些设计决策背后的意图。在快速推进的初创公司或大公司中，规格、代码、测试、PRD、工单等都由 Claude Code 生成，人们只向 AI 提问而不再思考，最终导致缺乏整体规划。文章指出，即便手写代码可能式微，理解系统、架构、意图与设计仍有助于成为更好的工程师，而可维护性始终是最终挑战，因为生成越容易，需要维护的东西就越多。

作者澄清自己并非说产品经理将取代工程师，而是认为工程本身正在向产品管理演变。分歧在于：一方认为AI反复重写会陷入长期维护v0.0.1的困境，重写必然带来新边缘案例和故障，且无人从中学习；另一方则认为这些担忧早已存在，软件工程的难点从来不在写代码或通过测试，而在于厘清需求、处理不规范接口和验证流程，这些才是真正无法外包的核心。

## Parley：基于IRC的联邦式去中心化聊天

Parley: Federated, decentralised chat that speaks plain IRC

**发布时间**: 2026-09-28

**链接**: [https://git.mills.io/prologic/parley](https://git.mills.io/prologic/parley)

**描述**:

Parley 是一个去中心化的联邦聊天网络，每个用户或团队为自己的域名运行小型实例，实例通过 DNS 和 well\-known 身份文档互相发现，并以 HTTPS 交换签名消息，同时向普通 IRC 客户端（如 irssi、WeeChat、Textual）呈现整个联邦网络，无需插件。身份形如 alice@foo\.com，用户可直接用 /msg alice@foo\.com 跨实例私聊，两个此前互不认识的实例会即时建立联邦。项目目前是端到端可运行的概念验证，尚未加固。

**评论要点**:

发送端和接收端的线路速率不一致，这本质上只是带宽耗尽的问题。有人则认为XMPP协议很糟糕，但电子邮件和ActivityPub同样如此，或许联邦式架构本身就存在根本缺陷。分歧在于：一方将问题归因于简单的带宽限制，另一方则质疑联邦协议的整体设计。
