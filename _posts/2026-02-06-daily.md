## 中情局将逐步停用《世界概况》

CIA to Sunset the World Factbook

**发布时间**: 2026-02-05 12:53

**链接**: [https://www.abc.net.au/news/2026-02-05/cia-closes-world-factbook-online-resource/106307724](https://www.abc.net.au/news/2026-02-05/cia-closes-world-factbook-online-resource/106307724)

**描述**:

美国中央情报局宣布将停止出版《世界概况》，这一免费在线资源被全球数百万人使用。该手册自二战时期作为内部机密项目启动，后于1975年向公众开放，提供各国易于理解的标准化基础信息。尽管未说明关闭的具体原因，但此举发生在特朗普政府向中情局全员提供买断、并计划大幅削减该机构岗位的背景下。中情局仅表示该出版物已“日落”，鼓励读者通过其他方式探索世界。

**评论要点**:

评论讨论了《世界概况》停更的原因，主要归因于数据获取成本上升和审核工作量巨大。关键点包括：第三方数据源转为昂贵订阅或许可模式，导致维护困难；为确保258个实体数千数据点的准确性，需情报官员进行繁重核查，这与“少花钱多办事”的指令相冲突。有观点认为这符合“制造同意”盛行的时代背景，并引用尼采“没有事实，只有诠释”。另有争议涉及美国海外军事基地的建立方式，部分评论者认为日本和德国初期是武力威胁下的结果，但地图显示大多数基地并非依靠“武力”建立。

We tasked Opus 4.6 using agent teams to build a C Compiler

**发布时间**: 2026-02-05 19:07

**链接**: [https://www.anthropic.com/engineering/building-c-compiler](https://www.anthropic.com/engineering/building-c-compiler)

**描述**:

研究人员通过“智能体团队”方法，让16个Claude实例并行协作，在无人持续干预下从零构建了一个基于Rust的C语言编译器。该项目耗时两周，消耗约2000次会话和2万美元API成本，最终产出10万行代码的编译器，能成功编译Linux 6.9内核及多个开源项目。实验揭示了设计长期自主智能体系统的关键：需构建完善的测试环境与反馈机制，使模型能自主判断进度；通过任务锁定机制解决并行冲突；利用专业化分工提升效率。尽管成果显著，但编译器仍存在性能不足、部分功能依赖GCC等局限。该实验展示了LLM在复杂项目上实现自主开发的潜力，也突显了完全自主开发伴随的质量与安全风险。

**描述**:

文章揭示了以OpenClaw为代表的AI助手生态系统的重大安全风险。其核心问题在于，“技能”通常只是Markdown文档，却包含可直接执行的指令或恶意链接，本质上成为了恶意软件的传播渠道。作者发现，一个热门“技能”就是macOS信息窃取木马的投放载体，且这并非个例，而是一场有组织的攻击活动。

这种攻击之所以危险，是因为它利用了人们对文档的信任以及快速执行安装步骤的习惯。在智能体环境中，阅读说明与执行命令的界限已模糊，恶意技能就是包裹在友好文档中的远程执行代码。

文章强烈警告：切勿在公司设备上运行此类工具。如果已运行，应立即联系安全团队，并视作潜在安全事件处理，优先轮换所有凭证和会话。对于技能注册中心和框架开发者，必须将技能视为可执行代码进行严格审核与沙箱隔离。未来的解决方案是构建缺失的信任层，为智能体实施细粒度、可撤销且有时限的权限控制。

**评论要点**:

评论讨论了使用grep作为代码审查第一阶段的安全优势，因为它无法被提示注入攻击，能可靠检测如base64编码的curl命令等风险。第二阶段使用LLM审查虽有效但易受提示注入影响，例如模型可能被诱导忽略指令。作者引用并质疑了“林纳斯定律”，指出Heartbleed漏洞证明“足够多的眼睛”理论前提是审查者真正关注。针对LLM，提出了“威利森定律”的幽默观点：即使使用多个LLM，提示注入风险依然存在。讨论涉及了base64、bash、curl等技术术语，并强调了工具链中结合规则匹配与AI审查的利弊。

## 2026年了，直接使用Postgres吧

**发布时间**: 2026-02-05 21:24

**链接**: [https://www.tigerdata.com/blog/its-2026-just-use-postgres](https://www.tigerdata.com/blog/its-2026-just-use-postgres)

**描述**:

文章核心观点是反对过度使用多种专用数据库，主张在绝大多数场景下使用PostgreSQL。作者指出“为特定工作选择专用工具”的理念会导致数据库数量激增，带来运维、备份、安全、监控和故障排查的复杂性，尤其在AI时代，这会给需要快速创建测试环境的智能体带来巨大障碍。PostgreSQL通过其成熟的扩展机制（如pg_textsearch、vector、timescaledb等）已能提供与专用数据库同等或更优的搜索、向量、时序、队列等功能，且避免了数据同步、多系统协调等隐藏成本。对于99%的公司而言，单一、强大且统一的PostgreSQL是更简单、高效且经济的选择。

## 公司即代码

Company as Code

**发布时间**: 2026-02-05 12:56

**链接**: [https://blog.42futures.com/p/company-as-code](https://blog.42futures.com/p/company-as-code)

**描述**:

作者作为一家软件公司的成员，观察到公司运营高度数字化，但核心的组织结构、政策和流程却仍依赖静态文档管理，这造成了效率低下和审计负担。他提出一个革命性构想：将整个组织“代码化”，即创建一种可编程、可版本控制、可查询和自动验证的动态数字表示，称为“公司即代码”。这类似于“基础设施即代码”的理念，旨在通过声明式语言和图形数据库等技术，将人员、政策、系统和合规要求明确关联起来。这种模式能实现自动化合规检查、影响分析，并在实施前模拟组织结构变更，从而大幅提升运营透明度、审计效率，并将资源从繁琐的文档工作中解放出来，专注于创造价值。尽管面临组织复杂性和工具易用性等挑战，但作者认为现有技术已为此奠定了基础。

## 现代化Linux交换机制：引入交换表

Modernizing Linux swapping: introducing the swap table

**发布时间**: 2026-02-05 06:58

**链接**: [https://lwn.net/SubscriberLink/1056405/e728d95dd16f5e1b/](https://lwn.net/SubscriberLink/1056405/e728d95dd16f5e1b/)

**描述**:

Linux内核的交换子系统在6.18版本中迎来了一项重要重构。核心改进是引入了“交换表”来取代原有的XArray数据结构，以简化并优化交换代码。此前，系统使用两层独立的簇管理机制（64MB的`swap_info_struct`数组和2MB的交换簇），导致操作复杂且存在争用。新方案将状态信息与现有的交换簇直接关联，用紧凑的C语言数组替代XArray，从而减少了内存开销和查找开销。这一改变提升了交换操作的局部性和可扩展性，据称在基准测试中带来了约5-20%的性能提升。此次重构是简化内核交换代码长期项目的第一步，后续版本预计将有更多改进。

**评论要点**:

讨论主要围绕交换分区与交换文件的优劣展开。支持交换分区者认为其设置简单、稳定可靠，能自动通过标签识别，且避免了交换文件在btrfs等文件系统上的限制（如快照问题）。支持交换文件者虽承认其技术更优，但指出休眠等功能需要计算文件偏移等复杂操作，流程繁琐且脆弱。关于交换空间的作用，共识是即使内存充足，交换空间也能通过将不活跃内存换出、腾出空间给磁盘缓存来提升系统性能，且过量配置除占用磁盘外无害。建议桌面系统配置至少4GB交换空间，并监控使用情况，若超过1GB则应考虑增加内存。在服务器场景中，交换空间有助于缓解恶意登录导致的DDOS攻击，避免系统因内存耗尽而崩溃，是成本较低的保护措施。
