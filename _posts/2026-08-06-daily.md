## GitHub Actions 和 Pages 服务可用性下降

GitHub Actions and Pages are experiencing degraded availability

**发布时间**: 2026-08-06

**链接**: [https://www.githubstatus.com/incidents/qcvjkzcs7j74](https://www.githubstatus.com/incidents/qcvjkzcs7j74)

**描述**:

GitHub 官方状态页记录了此次影响 GitHub Actions 与 Pages 的可用性降级事件。事件期间，工作流运行出现启动失败或中途失败、任务长时间排队甚至超时，Actions REST API 部分请求报错，自托管运行器注册时出现错误或限流，Webhook 触发被节流，导致大量 push 和 pull request 事件无法触发新工作流。工程团队定位到运行器被分配无效任务等问题并部署修复，任务成功率逐步回升至 99%，系统级队列已排空，Webhook 触发的工作流恢复全吞吐量，Pages、Copilot 代码审查等显示恢复，但 GitHub Enterprise Importer 迁移仍暂停作为预防措施。

**评论要点**:

GitHub的可用性下滑与LLM带来的代码量激增形成鲜明对比，但代码质量并未同步提升，反而充斥着“LLM sloppy-pasta”式的粗糙产物。评论者质疑，即便提交量增长十倍，实际生产力与创新应用并未兑现，暗示AI辅助开发可能只是制造了更多低质量代码，而非真正的效率革命。分歧在于，有人将责任归咎于LLM工具本身，认为其鼓励了“量大于质”的编码习惯；另一些人则强调问题出在开发者过度依赖AI，缺乏人工审查与架构思考，导致技术债累积。整体上，评论对当前AI编程热潮持怀疑态度，认为其宣传效果远大于实际价值。

## 人类在4万次游戏运行中批准AI代理命令时，漏掉了三分之一的威胁。

Humans missed 1 in 3 threats approving AI agent commands across 40k game runs

**发布时间**: 2026-08-06

**链接**: [https://scalex.dev/blog/ai-agent-permissions-stats/](https://scalex.dev/blog/ai-agent-permissions-stats/)

**描述**:

这篇文章基于作者开发的一款浏览器游戏数据，分析了人类在审批AI编码代理命令时的表现。游戏记录了超过4万次运行和40\.9万次批准/拒绝决策，结果显示玩家平均漏掉三分之一的威胁（准确率66\.3%），其中明显的破坏性命令（如rm \-rf /）漏过率最低（11\.7%），而窃取凭据的越权命令漏过率高达35%。最容易被漏过的是npm run类命令（如npm run analyze被批准64\.7%），因为玩家常忽略历史日志中的恶意载荷。文章还指出审批疲劳导致越到后期漏过率越高，同时玩家也会过度拦截良性命令（如npm config set被误拦59%），并讨论了人类在环作为安全防线存在的局限与缓解建议。

**评论要点**:

评论者以Windows和Linux为例，对比了基于能力的权限系统与传统访问控制模型的差异。其核心观点是：在传统模型中，程序一旦被攻破即可获得用户全部权限，而能力系统通过OS级强制限制程序仅能执行预设操作，即使程序被攻击也无法越权。评论还指出Linux的/proc或/sys等特殊文件系统可能引发副作用，但未深入展开。分歧点在于对“文件系统访问”概念的理解——一方认为这是抽象权限，另一方则强调其可能触发内核级风险。整体上，评论者更推崇能力系统的精细化控制，但承认其实现复杂度较高。
