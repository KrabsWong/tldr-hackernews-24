## 六成美国消费者称品牌信息中提及AI令人反感

**发布时间**: 2026-06-17

**链接**: [https://wpvip.com/future-of-the-web-2026/](https://wpvip.com/future-of-the-web-2026/)

**描述**:

## Lore——可扩展的开源版本控制系统

Lore – Open source version control system designed for scalability

**发布时间**: 2026-06-17

**链接**: [https://lore.org/](https://lore.org/)

**描述**:

Lore 是由 Epic Games 维护的下一代开源版本控制系统，专为应对大规模数据和团队协作而设计，特别优化了代码与大型二进制资产的结合，适用于游戏与娱乐项目。其核心特性包括：分钟级本地模式快速启动、按需扩展、高效复用数据与按需下载、免费分支管理、可验证的篡改证据历史、直观的 CLI 界面，以及支持 C/C++、C#、Rust、Go、Python 和 JavaScript 的全表面 API。架构上，Lore 采用中心化、内容寻址的存储方式，通过 Merkle 树表示仓库状态，并使用不可变的修订链实现加密完整性；针对大文件进行分块存储，支持稀疏工作区按需获取数据，通过服务端缓存提升吞吐量，分支为轻量级可变引用，切换快速无数据重复。Epic 还提供了 Lore 库、服务器及 CLI，以及 JavaScript、Python、C#、Go 等多语言 SDK，所有代码完全开源。

**评论要点**:

Git分布式设计在二进制文件（如媒体文件、XML等非行级文件）的合并上存在明显短板，但文本文件的离线优先和易合并特性使其成为大多数开发场景的合理权衡。尽管有大量教程，这更多源于其普及度而非设计缺陷。相比之下，P4需要学习更多概念，而Git的核心命令能直接覆盖日常版本控制需求的98%。

## RFC 10008: 新的HTTP查询方法

RFC 10008: The new HTTP Query Method

**发布时间**: 2026-06-17

**链接**: [https://www.rfc-editor.org/info/rfc10008/](https://www.rfc-editor.org/info/rfc10008/)

**描述**:

RFC 10008 定义了 HTTP QUERY 方法，用于执行安全且幂等的请求。与 GET 相比，QUERY 允许在请求体中传递大量数据，避免 URI 长度限制；与 POST 相比，QUERY 明确声明安全性和幂等性，支持缓存和自动重试。服务器可为查询本身或查询结果分配 URI，以便后续通过 GET 访问。该方法填补了 GET 和 POST 之间的空白。

**评论要点**:

评论核心观点：HTML表单目前仅支持GET和POST，导致用户需借助hack（如_method=DELETE）来实现DELETE等语义，破坏HTTP幂等性并增加应用逻辑。作者认为应扩展表单支持所有人类相关的HTTP动词，使URL清晰且无需额外处理。此外，讨论指出GET请求缓存依赖精确URL，因参数编码方式多样，而若显式标记为multipart或url-encoded则参数顺序无关（但仅POST使用且不应缓存）。最后，补充PUT是幂等的，但PATCH可能非幂等（如JSON Patch允许向列表添加元素）。

## 展示：高分辨率神经细胞自动机

Show HN: High-Res Neural Cellular Automata

**发布时间**: 2026-06-17

**链接**: [https://cells2pixels.github.io/](https://cells2pixels.github.io/)

**描述**:

## 为什么 stdx 不在 crates.io 上？

Why stdx is not on crates.io

**发布时间**: 2026-06-17

**链接**: [https://kerkour.com/stdx-cratesio](https://kerkour.com/stdx-cratesio)

**描述**:

stdx 未发布在 crates.io 上，主要原因有二：一是 crates.io 缺乏命名空间，导致包名冲突和安全隐患（如恶意软件伪装）；二是包仓库本身存在严重供应链攻击风险，包括凭据泄露、代码篡改、中间人攻击、域名抢注等。作者认为，与其在复杂系统上打补丁，不如采用更简单、安全的设计，例如通过 git 直接分发代码。

**评论要点**:

评论的核心观点包括：一、**命名空间劫持问题**：质疑谁有权获得知名名称（如“apache”），是否参考域名注册机制，以及用户抢注这些名称是否构成问题。二、**供应链安全**：认为通过维护可信仓库和提交哈希列表即可审计依赖，而非依赖命名空间。作者对“当前供应链问题是否严重”存疑，并提到类似工具（如cargo-vet）可能更适合生态现状。三、**对Go依赖管理方式的澄清**：反驳“Go项目使用随机Git哈希”的说法，指出通常使用带版本字符串的Git标签，并将标签锁定到哈希以防止篡改。
