## 大型语言模型正在侵蚀我的软件工程职业生涯，我不知该怎么办

LLMs are eroding my software engineering career and I don't know what to do

**发布时间**: 2026-06-07

**链接**: [https://human-in-the-loop.bearblog.dev/llms-are-eroding-my-software-engineering-career-and-i-dont-know-what-to-do/](https://human-in-the-loop.bearblog.dev/llms-are-eroding-my-software-engineering-career-and-i-dont-know-what-to-do/)

**描述**:

一名拥有10年经验的软件工程师发现，大型语言模型正在侵蚀其职业优势。起初，他专注于金融支付领域，积累了大量领域知识（如PCI合规、记账等），并认为这是AI无法取代的。但入职一家全力拥抱AI的金融公司后，他发现LLM能出色地完成设计文档撰写和系统架构规划，他引以为傲的领域知识逐渐变得“无用”。

随后，他将希望寄托在调试与分布式系统等复杂问题上。然而，随着Claude Code、Codex等工具的普及，LLM不仅能写代码，还能通过分析日志和追踪来协助调试，甚至能直接修复bug。在部署Agentic系统后，AI能自动捕捉异常并修复，工程师的角色从“写代码”变成“监督AI工作”。

最终，他的职业定位变为“AI编排员”，价值取决于监督和修复AI的独特能力。但AI系统已能自我修复，这让他的角色变得尴尬。文章总结道，LLM正从编码到高级调试逐步侵蚀软件工程的核心技能，使工程师过去十年的经验积累面临贬值。

**评论要点**:

评论核心观点：建立工作声誉的关键是培养快速适应新事物、新流程的能力，通过实践积累经验。作者以原型机械师经历为例，说明不断接触新材料、新工艺如何训练出高效学习能力，从而在工作中脱颖而出。建议保持好奇心，动手制作各种物品，并分享成果，主动承接他人需求，以此逐步建立个人声誉。

**描述**:

Anthropic 目前仅发布 macOS 和 Windows 版 Claude Desktop，Linux 用户只能依赖第三方打包（如 aaddrick/claude-desktop-debian，约 4.5k star），存在非官方签名、凭证安全风险。Claude Code CLI 虽原生支持 Linux，但桌面版缺失导致 Linux 用户无法使用桌面扩展、电脑控制、桌面听写和 Cowork 等图形功能。Cowork 在 macOS 上通过启动 Ubuntu 22.04 VM 运行 Claude Code 二进制，内部已依赖 Linux 执行路径，社区项目（johnzfitch/claude-cowork-linux）可直接在 Linux 上原生运行，说明技术可行性。Anthropic 已有 Linux 软件分发流程（apt、dnf、apk 仓库）。Stack Overflow 2025 调查显示 27.7% 专业开发者使用 Ubuntu 作为主系统。文章请求 Anthropic 发布官方 Linux 构建（目标 Ubuntu LTS 和 Debian 的签名 .deb），或至少给出明确不支持原因，以消除用户安全隐患和平台缺失。

## Linear为何如此之快？技术解析

How's Linear so fast? A technical breakdown

**发布时间**: 2026-06-07

**链接**: [https://performance.dev/how-is-linear-so-fast-a-technical-breakdown](https://performance.dev/how-is-linear-so-fast-a-technical-breakdown)

**描述**:

Linear 应用之所以极快，关键在于它将浏览器作为主数据库（IndexedDB），颠覆了传统 CRUD 流程：用户操作直接在本地内存中同步更新 UI，再通过自研同步引擎异步推送到服务器，并通过 WebSocket 广播差异给其他客户端。这种架构彻底消除了网络请求导致的等待，UI 响应不依赖网络延迟。文章强调，构建快速 Web 应用的核心是隐藏网络请求，避免加载态。Linear 从项目第一天就以此思路设计同步引擎，而普通开发者可通过乐观更新（如 TanStack Query、SWR 等库）接近类似效果。此外，文章还提及首次加载优化（预加载数据）、流畅动画等细节。

**评论要点**:

Linear应用的实际性能问题比过度优化更值得关注。首先，真正追求速度应避免复杂缓存或hack，而选择快速的前后端技术（如SolidJS、优化数据库），否则复杂缓存只会导致性能瓶颈。现代硬件（多核CPU、大内存、高速网络）本应无需这种复杂度，用JS后端、Postgres和笨重前端框架却宣称高性能是自欺欺人。其次，Linear作为CRUD应用，通常不需要本地数据库副本——后端正常处理就应只需几毫秒，本地副本反而造成不一致。最后，用户反馈Linear首次加载常需几十秒，远非“快”的应用，优化更新从300ms降到几ms没有意义，因为根本的加载速度问题未解决。核心观点：Linear的性能问题源于架构或框架选择，而非缺乏花哨优化，解决基础加载慢比局部加速更重要。

**描述**:

一位设计师分享了自己从怀疑AI到依赖Claude（AI编码助手）的转变。过去，他习惯用Figma设计原型、撰写文档，再与工程师反复沟通实现。如今，他直接用Claude编写可运行的原型，并在实际代码库中迭代、测试和优化，省去了Mockup和文档等中间环节。这种工作流使设计更快、更自由，实现了以往难以达成的细节改进。然而，缺点在于，当设计师直接提交完整功能后，评审者可能失去对功能设计发表意见的机会，变成了纯粹的代码审查。

**评论要点**:

评论的核心观点包括两部分：一是筛选客户时，应主动让那些不合适的客户自行退出，无需顾虑是否对其业务不利；二是AI虽能加速原型开发和提升代码产出效率，但无法替代人类专家在关键思考、假设验证和领域知识方面的作用，否则会导致高成本试错或生产环境中的严重问题。真正的工程瓶颈从来不是代码量，而是需要懂行的专家完成项目，无论他们是否借助AI辅助。

## 展示 HN：Lathe——用LLM学习新领域，而非跳过它

Show HN: Lathe – Use LLMs to learn a new domain, not skip past it

**描述**:

Lathe 是一个利用 LLM 生成动手实践技术教程的开源项目。它根据用户提示生成单篇或多篇系列教程，并在专为学习设计的本地 UI 中引导用户亲手操作。用户可以通过内置技能向 LLM 提问、验证教程内容或扩展新部分。支持搜索、过滤和管理教程库，每个教程都记录来源、模型和提示信息。安装方式包括 Homebrew、安装脚本、Go 安装及源码编译，并可将技能集成到 Claude Code、Cursor、Codex 等 AI 工具中。项目旨在通过实践方式帮助用户学习编程，而非让 LLM 替用户思考。

**描述**:

阈限主义（Liminalism）作为一种由大众策展的数字运动，已成为当代最具代表性的审美。它源于对“中间状态”空间的探索——如废弃商场、空荡走廊等，这些场景既熟悉又诡异，充满怀旧与不安。文章以宾夕法尼亚州的世纪三购物中心为例，这座曾是世界第三大商场如今只剩空壳，其照片在脸书“阈限摄影”群组中展现了衰败的凄凉。这一审美可追溯至2019年4chan上的恐怖故事《The Backrooms》，描绘了一个由无限重复的黄色房间构成的炼狱空间，充满潮湿地毯和荧光灯的气味。这些非场所——空荡荡的机场大厅、深夜办公室、关闭的杂货店——反映了人们对当下晚期资本主义的荒诞体验。阈限主义成为对残酷现实的最直接艺术反应，融合了波哥大和丹尼列夫斯基式的超现实感，凸显了当代生活的疏离与忧郁。

**评论要点**:

评论者认为“liminal spaces”流行缺乏深层意义，仅是因神秘感吸引人的一时风潮，如同将“spooky”审美强行赋予高深内涵一样空洞。他分享了自己早年拍摄空无一人的圣克鲁兹栈道照片的经历，指出无需依靠衰败或单调色调，只需在正常光线和色彩下移除人群，即可营造出同样的诡异感，而这种效果正是现代liminal space的核心：在人类密集之处展现空无一人，引发“无人观察时世界在做什么”的永恒疑问。随着世界愈发拥挤而孤独，人们好奇空间在人群散去后的状态，这种探索才是该审美真正触动人心之处。

**发布时间**: 2026-06-07

**链接**: [https://arxiv.org/abs/2601.14470](https://arxiv.org/abs/2601.14470)

**描述**:

本文研究了基于LLM的多智能体系统（LLM-MA）在软件工程任务中的token消耗模式。以ChatDev框架执行30个软件开发任务为例，将其内部阶段映射至设计、编码、代码补全、代码审查、测试和文档等阶段，并量化分析token分布。研究发现，迭代的代码审查阶段消耗了最多token，平均占比59.4%；输入token在所有token中占比最大，平均为53.9%。这表明代理软件工程的主要成本并非初始代码生成，而是自动细化与验证环节。该研究方法有助于从业者预测费用、优化工作流，并推动开发更高效的多智能体协作协议。

Podman 6 在 machine 功能上进行了重大改进，主要解决多 provider 环境下的可用性问题。在 Podman 5 中，不同 provider（如 libkrun、applehv）创建的虚拟机相互隔离，CLI 默认仅识别默认 provider 的机器，需通过 `--all-providers` 参数才能查看全局，且无法直接通过名称操作非默认 provider 的机器。Podman 6 优化了跨 provider 的管理：一是默认显示所有 provider 的机器列表，去除了 `--all-providers` 开关；二是支持直接通过机器名进行 `stop`、`start` 等操作，无需考虑其 provider；三是新增 `--provider` 命令行选项，允许在 `podman machine init` 时指定非默认 provider 创建机器。这些改动简化了多 provider 场景下的使用流程，提升了用户体验。

**评论要点**:
