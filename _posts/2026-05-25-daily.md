## 醒来！16b

Wake up! 16b

**发布时间**: 2026-05-24

**链接**: [https://hellmood.111mb.de/wake_up_16b_writeup.html](https://hellmood.111mb.de/wake_up_16b_writeup.html)

**描述**:

这篇文章介绍了作者用16字节x86实模式汇编语言创作的程序“wake up!”。程序在DOS系统下运行，利用视频内存作为计算空间，同时绘制无限Sierpinski分形并驱动扬声器发声。核心代码通过循环执行`lodsb`、`sub si, byte 57`、`xor [si], al`和`out 61h, al`等指令，巧妙地利用内存初始化为0x20的特性，结合加性前缀和算法，使每步产生的二项式序列转化为图形和声音。作者强调，该程序揭示了数学与感官之间的深层联系，远超简单噪声生成，堪称“将Sierpinski声转化为矩阵雨”的极简实现。

**评论要点**:

评论者对极小的生成代码（16字节）表示惊叹，但指出实际搜索空间虽大（约2^75），由于需要访问显示内存、声音端口并在循环中变化，加上指令有效性限制，真正有复杂性和美感的输出极少。因此，不太可能找到大量有趣的音视频演示，搜索空间与实际有效输出之间相差9个数量级。

**描述**:

澳大利亚一项发表在《自然》旗下期刊的研究证实，四天工作制（100:80:100模型：100%薪资、80%工时、100%产出）切实可行。研究追踪了15家澳大利亚公司（2022-2024年），结果：14家决定继续实行，无一报告生产力下降，6家产量上升，其余持平。研究由迪肯大学John Hopkins教授主导，通过访谈进行，各公司自行定义生产力指标。关键发现：该模式迫使企业削减无效会议、自动化或重新分配任务，实现更专注的高质量工作。六家公司明确表示主要动机是减少员工倦怠（调查显示半数澳洲员工正经历倦怠）。一家公司因处于内部变革期而退出试验。结论：四天工作制不仅可行，还能提升效率与员工福祉。

## 约束衰减：LLM代理后端代码生成的脆弱性

Constraint Decay: The Fragility of LLM Agents in Back End Code Generation

**发布时间**: 2026-05-24

**链接**: [https://arxiv.org/abs/2605.06445](https://arxiv.org/abs/2605.06445)

**描述**:

这篇论文系统研究了LLM代理在生成后端代码时，面对严格结构约束（如架构模式、数据库、对象关系映射）的表现。通过80个新代码生成和20个功能实现任务，覆盖8个Web框架，使用统一API契约并辅以端到端行为测试和静态验证，作者发现了“约束衰减”现象：随着结构约束增加，代理性能显著下降。从基线到完全指定任务，配置强的代理断言通过率平均下降30个百分点，弱的近乎为零。框架敏感性分析显示，代理在显式框架（如Flask）中成功率高，而在约定重于配置的框架（如FastAPI、Django）中表现差。错误分析表明，数据层缺陷（如错误查询组合、ORM运行时违例）是主要失败原因。研究指出，同时满足功能需求和结构约束仍是编码代理的重大挑战。

**评论要点**:

评论核心观点：1）如果不采用良好开发实践，AI长期维护的代码会变得混乱；2）优秀的开发者擅长隔离系统、保持简单性并自动化繁琐工作，这些特质有助于引导AI产出可管理的结果；3）作者开发了engine.build工具，通过结构化外部代理编排器，在明确约束下构建系统，确保输出符合规范，虽需多轮审查但能获得可靠结果；4）将AI简单称为“文本预测”低估了其在模糊函数推断中的创造力。

## 用Jujutsu战胜Git繁琐疲劳

Defeating Git Rigour Fatigue with Jujutsu

**发布时间**: 2026-05-24

**链接**: [https://ikesau.co/blog/defeating-git-rigour-fatigue-with-jujutsu/](https://ikesau.co/blog/defeating-git-rigour-fatigue-with-jujutsu/)

**描述**:

作者提出一种使用 jujutsu（jj）解决 “git 严谨疲劳” 的工作流：开发大型特性时，很难始终保持良好提交历史（如类型定义、数据库函数等分离）。传统做法容易变成一堆混乱的临时提交，后期难以整理。

作者的方法：先随意写代码，所有变更混合在一个“everything commit”中。然后**创建理想的空提交历史**（如 `jj new -B messy-first -m 'red'` 创建名为 “red” 的空提交，再创建 “blue” 等），再把所有实际变更压缩至一个提交，再用 `jj squash -i` 交互式地将不同代码片段精准归入对应空提交。最终得到一个整洁的提交历史，而中间临时提交被清空。

这种方法比强制保持严格提交更省力，优于 `jj absorb`（自动分配可能出错）和 `jj squash`（易陷入合并冲突）。也优于 `jj split`（需多次拆分）。缺点是无法保证每个独立提交都能编译。作者形容为“像洗一大堆衣服一样做提交”。

**评论要点**:

用户的核心观点：未曾正式学习Git，但发现使用命名分支的人常遇到困难，而使用jj的rebase命令却非常简单直接。对jjui相比lazyjj的优势感到困惑，尝试后仍不理解。最终接受了squash PR的做法，并感慨过去追求“好提交”浪费了时间。
