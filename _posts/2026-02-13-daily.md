## 一个下午改进15个LLM的编码能力：仅改变了测试框架

Improving 15 LLMs at Coding in One Afternoon. Only the Harness Changed

**发布时间**: 2026-02-12 13:30

**链接**: [http://blog.can.ac/2026/02/12/the-harness-problem/](http://blog.can.ac/2026/02/12/the-harness-problem/)

**描述**:

当前AI编程工具的讨论过度聚焦模型性能，而忽略了关键瓶颈——编辑工具本身。文章通过对比16种模型在三种编辑格式下的表现发现，模型并非失败主因，编辑工具格式才是关键变量。仅将编辑格式从传统的“查找替换”改为基于行哈希的锚点引用，就使多数模型成功率显著提升，其中Grok Code Fast 1从6.7%跃升至68.3%，同时节省约20-30%的token消耗。这证明优化工具层比升级模型更具成本效益。然而，主流厂商却倾向于封锁第三方工具集成，阻碍了开放生态的创新。文章主张，解决工具层问题才是提升AI编程实用性的高效路径，这一进步应由开源社区共同推动，而非个别公司私有化控制。

**评论要点**:

该评论讨论了Peen CLI工具，它能让本地Ollama模型有效调用工具。作者指出，尽管项目尚不成熟，但通过几小时的提示工程和响应处理代码优化，就能显著提升小型本地模型的输出效果。技术讨论涉及性能分析，认为传统方法可能涉及O(N)复杂度的str_replace操作和O(N^2)的读写开销，而新工具可能实现O(1)操作。争议点在于有评论质疑其相对于现有MCP服务器的优势，后者已能通过暴露工具来执行查询，暗示可能无需重复造轮子。关键术语包括Ollama、CLI、MCP服务器、O(1)、O(N)、O(N^2)和str_replace。

## Apache Arrow迎来十周年

Apache Arrow is 10 years old

**发布时间**: 2026-02-12 13:13

**链接**: [https://arrow.apache.org/blog/2026/02/12/arrow-anniversary/](https://arrow.apache.org/blog/2026/02/12/arrow-anniversary/)

**描述**:

Apache Arrow项目于2016年2月5日正式成立，现已迎来十周年。该项目成功实现了其核心目标：为列式数据交换提供高效、持久且与系统无关的标准。Arrow最初旨在解决内存中的互操作性问题，与持久存储格式Parquet形成互补。其首个版本0.1.0于2016年10月发布，定义了核心数据类型。尽管格式规范在后续演进中保持了高度稳定，仅对联合类型（Union）的有效性位图进行过一次重大但影响甚微的破坏性变更。项目从最初仅C++和Java两个实现，已发展成拥有庞大生态的系统，涵盖多种编程语言的官方库及多个子项目（如DataFusion）。Arrow格式已被众多第三方工具广泛采用，并与Parquet紧密结合使用。社区秉持共识驱动，在保持规范稳定的同时，持续欢迎新的贡献与用例。

**评论要点**:

评论指出云存储降价未惠及云服务商，自托管存储则因AI热潮而更昂贵。关于Apache Arrow，评论认为其十周年文章预设读者已了解该技术，建议新手查阅文档。技术讨论强调列式存储格式（如Arrow）无法高效支持单文件内的逐行追加；虽有通过文件内分配区域（arenas）的变通方案，但会导致严重的写入放大问题——原本单块写入的行数据需按列拆分为多个块写入，显著影响性能。

## 代码行数卷土重来（且比以往更糟）

Lines of Code Are Back (and It's Worse Than Before)

**发布时间**: 2026-02-12 15:35

**链接**: [https://www.thepragmaticcto.com/p/lines-of-code-are-back-and-its-worse](https://www.thepragmaticcto.com/p/lines-of-code-are-back-and-its-worse)

**描述**:

软件行业曾就“代码行数（LOC）是糟糕的指标”达成共识，因为它鼓励编写冗长代码且无法衡量实际价值。但随着AI代码生成工具的普及，行业竟重新开始追捧LOC，各大科技公司竞相报告AI生成代码的百分比，并将其视为成就。这实则更糟：AI使得这一指标被无限滥用，因为生成代码的成本近乎为零，大量产出却意味着更多重复代码、更少重构、更高缺陷率以及更低的理解度。当前流行的“接受率”指标同样存在缺陷。文章指出，真正应衡量的是结果而非输入，例如功能上线时间、代码半衰期、缺陷溯源和团队对代码的理解覆盖率。衡量这些虽更困难，却能反映软件质量和团队效率的真实情况。LOC从未衡量过真正的瓶颈——理解、设计与判断，在AI时代尤其如此。

**评论要点**:

评论指出公司常将单行AI自动补代码计为AI生成代码，显著夸大相关指标。有观点认为减少代码行数同样能影响此类游戏化指标。讨论涉及对AI代码审查的担忧，传统上依赖程序员智力（"g-loaded"）来保证代码质量，而AI生成的高质量表象可能破坏审查者的潜意识判断。争议点在于自动化程度的平衡：一种观点支持有限自动化（如仅维持航向和气压高度的自动驾驶仪，超出能力时发出警报），另一种则追求全自动化（如使用GPS、雷达、LIDAR的自主无人机），中间地带存在风险。
