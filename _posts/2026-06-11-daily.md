## 构建HTML优先网站，用户一夜翻倍

Building an HTML-first site doubled our users overnight

**发布时间**: 2026-06-10

**链接**: [https://mohkohn.co.uk/writing/html-first/](https://mohkohn.co.uk/writing/html-first/)

**描述**:

一位公用事业公司客户在申请服务时面临旧ASP表单或昂贵的人工流程，且因监管压力需保持96%以上的客户满意度。之前两次昂贵的尝试均告失败，其中一次外包的React应用上线仅三天就因用户投诉被撤下——该应用加载大量等待动画、全局JS状态，且将图片存入5MB的本地存储。作者决定用Astro构建HTML优先的网站：仅用Web组件渐进增强JS，确保在糟糕网络、老旧浏览器（如PSP）上正常工作，每个表单步骤单独页面并实时存储数据到后端。核心原则是公共服务必须人人可用。网站上线后，用户量在一夜之间翻倍。

**评论要点**:

服务器日志可以记录访客数量，但对单页应用（SPA）的页面浏览量统计存在局限，因为SPA的路由变化不一定会触发新的页面请求。评论引用2022年的一篇热门文章《SPAs Were a Mistake》，指出SPA并不理想。此外，评论者提到其妻子最初维护纯HTML/CSS网站，后来转向无JavaScript的HTML构建方式，暗示回归简单、无需JavaScript的开发模式更可取。

## π文件系统

πFS

**发布时间**: 2026-06-10

**链接**: [https://github.com/philipl/pifs](https://github.com/philipl/pifs)

**描述**:

πfs是一个幽默的实验性文件系统，声称通过将数据“存储”在圆周率π中，实现100%压缩，永不耗尽空间。其核心思想基于π是正规数的猜想，认为π包含所有可能存在的有限数字序列，因此所有文件都能在π中找到。实际使用时，将文件按字节拆分，在π中查找对应位置，但需要额外存储元数据（如文件在π中的索引）。项目仅作为概念验证，运行速度极慢，作者也承认其讽刺意味，旨在调侃数据存储和压缩领域的夸张说法。

**评论要点**:

评论以幽默讽刺的方式调侃了一种不切实际的数据编码方法：将字节拆分为比特，然后在π或e的二进制展开中查找这些比特的位置。作者指出π的二进制展开不实用（11.0010...），而e的二进制展开为10.1011...，并提议使用e的小数部分比特进行编码——只需将要编码的字节流与0xFF进行异或即可。这实际上是一个玩笑，因为异或0xFF相当于按位取反，完全不是真正的“索引查找”，意在嘲讽那些看似高深实则无用的编码方案。

## DiffusionGemma：4倍速文本生成

DiffusionGemma: 4x Faster Text Generation

**发布时间**: 2026-06-10

**链接**: [https://blog.google/innovation-and-ai/technology/developers-tools/diffusion-gemma-faster-text-generation/](https://blog.google/innovation-and-ai/technology/developers-tools/diffusion-gemma-faster-text-generation/)

**描述**:

DiffusionGemma是谷歌发布的一款实验性开放模型，采用文本扩散技术，在专用GPU上实现高达4倍的文本生成加速。该模型为26B参数的混合专家模型（仅激活3.8B参数），采用Apache 2.0许可，通过并行生成256个token（而非逐token顺序处理）显著提升推理速度（单张NVIDIA H100上超过1000 tokens/s，RTX 5090上超过700 tokens/s）。其双向注意力机制使每步生成的所有token相互关注，特别适合内联编辑、代码填充、序列预测等非线性任务。模型还具备实时自我修正能力。由于优先速度与并行布局，DiffusionGemma的整体输出质量低于标准Gemma 4，适合对速度敏感且可接受质量权衡的局部交互场景（如原型迭代）。开发者可通过微调进一步提升特定任务性能。

**评论要点**:

评论核心观点：一是CoT（思维链）的可读性几乎消失，引发安全担忧；二是认为扩散模型在概念上更酷；三是个人使用体验良好，提示词和评分标准影响效果，找bug作为搜索问题表现尤佳，借助非确定性与训练数据多样性，迭代集成能更有效覆盖问题空间；四是部分任务（如规划与路径搜索）受益显著，并引用DeepMind的Mind Evolution论文及作者此前发布的llm-consortium作为佐证。

## HelixDB：基于对象存储的图数据库

Show HN: HelixDB – A graph database built on object storage

**发布时间**: 2026-06-10

**链接**: [https://github.com/HelixDB/helix-db/tree/main](https://github.com/HelixDB/helix-db/tree/main)

**描述**:

HelixDB 是一个用 Rust 构建的 OLTP 图-向量数据库，旨在为 AI 应用提供统一平台，无需分别管理关系型、向量、图等独立数据库。其核心数据模型为图+向量，同时支持 KV、文档和关系数据。  
快速上手：安装 CLI 后，可通过 `helix chef` 一键引导（安装、建项目、启动实例、导入示例数据）；也可手动 `helix init` 初始化项目，`helix start dev` 启动本地实例（默认内存模式，重启数据丢失；`--disk` 可持久化），`helix query` 发送查询。  
查询通过 Rust 或 TypeScript SDK 编写为动态请求（POST /v1/query），无需构建或部署步骤。SDK 提供构建器 API，生成统一 JSON AST。文章附有 Rust 和 TypeScript 的增删用户示例代码。

**评论要点**:

用户首先祝贺项目发布，称赞网站和文档。然后询问该数据库是否可自托管，还是必须使用Helix Cloud——其侧边聊天功能引导用户前往Cloud，但起步价约600美元/月，超出实验预算。用户正在为智能体记忆应用寻找数据库，希望从自托管/免费方案开始；目前使用PostgreSQL尚可，但想开始接入服务器和聊天日志。

接着用户提到自己今年一直在用Rust开发图数据库，想了解项目在查询规划器和基数估计方面的决策。用户选择了EAV（实体-属性-值）图结构，这使得基数估计非常复杂，平衡质量、速度和查询语言表达力是个有趣的挑战。

最后用一个意大利语词“bellissimo”（非常美丽）表达赞赏。
